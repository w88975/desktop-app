## 为什么要留这份记录

上游是「一个版本 = 一个压缩提交」，没有可 cherry-pick 的粒度，每次同步都是人工判断「这条要不要」。
判断过程如果不写下来，三个月后没人说得清某个文件当初为什么没跟、或者某个上游改动是漏了还是故意不要的。

这份记录要能回答的问题：

- 上游 vX 到底改了什么？（不是罗列文件，是**分类**）
- 我们跟了哪些、没跟哪些，各自的理由是什么？
- 移植过程中发现了什么上游 diff 里没有、但我们必须处理的问题？
- 留了什么尾巴？

## 写法约定

- **一个版本一个文件**，文件名 `vX.Y.Z.md`。
- 变更**按性质分类**，不按文件列。上游一个版本动几十个文件，逐个列没有信息量；
  分成「实质功能变更 / 品牌域名替换 / 依赖与工具链 / 文档措辞」之后，通常只有第一类需要真的做决定。
- **忽略的部分必须写理由**，而且要写得能被反驳。「不需要」不是理由，「这批全是把 agents.craft.do
  换成 thecraftagents.com，我们两个域名都不用」才是。
- **写下 diff 之外的发现**。翻代码时必然会撞见上游没改、但我们有问题的地方（比如某个功能正在往
  第三方服务器发数据）。这些最有价值，专门列一节。
- 引用代码只写文件路径与符号名，不写行号 —— 行号在下次同步后必然失效。
- 记录的是**决策**，不是操作流水。命令怎么敲见 [../upstream-sync.md](../upstream-sync.md)。

## 流程

1. `git fetch upstream`，确认最新版本：
   `git for-each-ref refs/upstream-tags --sort=-v:refname --format='%(refname:short)' | head -5`
2. `git diff --stat upstream-tags/<已对齐版本> upstream-tags/<新版本>` 看波及面
3. 逐类判断要不要，**先把结论和理由跟人对齐**，再动手
4. 移植。对每个要动的文件，先确认它与上游是否已分叉：
   `git diff --numstat upstream-tags/<已对齐版本> HEAD -- <file>`
   —— 未分叉的可以直接 `git checkout upstream-tags/<新版本> -- <file>`，分叉的必须手工合
5. 验证：`bun run typecheck` + `bun test` + 项目自有门禁（见 [../dev/04-conventions.md](../dev/04-conventions.md)）。
   `bun test` 有存量失败，**跟基线比对**而不是要求全绿：
   `git stash -u && bun test > 基线 && git stash pop`
6. 按性质拆提交，每个能单独 revert
7. 在本目录写记录，更新上表和 [../upstream-sync.md](../upstream-sync.md) 顶部的已对齐版本
